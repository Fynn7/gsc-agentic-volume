## 一句话结论

两次运行失败的主因不是“阈值没调好”，而是**搜索方向反了，而且工具让模型无法纠正方向**。教堂模型（推断）的归一化密度约 0.28，两个 agent 的 40 次 `render_scene` 调用（39 次成功执行）全部使用 `tfStart ≥ 0.5`，一次都没有探测过 0.5 以下。同时，渲染器只暴露了单调高通传输函数，天然无法“只显示中等密度、隐藏更亮的玻璃壳和金属件”。

改进的总方向：**让程序负责几何和搜索，让模型只做语义选择**。核心做法是先自动建出“盒 ⊃ 球 ⊃ 内部物体”的结构树，再让模型在缩略图候选里做选择题，最后用体素手术和程序化验证收尾。

## 证据标签

文档里的每条结论都带来源强度，避免把推断当成事实：

- **【实测】** 直接从你上传的日志、截图或仓库代码读到或量到。
- **【推断】** 由实测数据推理得出，尚未经过实验验证。
- **【提案】** 设计建议，尚未实现。
- **【待验证】** 实施时必须先用小实验确认的假设。

## 项目快照

- 仓库：`gsc-agentic-volume`。Codex CLI 作为 harness，本地 Ollama 的 `qwen3.6:35b` 作为模型，通过 `scripts/renderer_mcp.py` 暴露 4 个 MCP 工具，渲染服务在 `src/`，原生渲染器是 `VirtualSampling/Raycaster`。
- 数据：TU Wien Christmas Present 工业 CT，使用的是 246×246×221 这一档。
- 任务原文：`Show me the chaple in the ball-like present inside the box - make the box invisible and the ball invisible, only make the chapel visible`
- 分析样本：两次运行 `run-20261024-200023-a026f1`（run a）和 `run-20261024-193758-90e262`（run b）的日志与截图，以及 8 张体素切片。

## 本文档集的局限

1. **原稿没有拿到体数据本体**。所有密度数值来自 run a 的 8 张切片（z=100/105/110/110 与 x=120/122/123/123）。本次整合复核了这些切片和运行日志，但结构树和密度带的结论仍需在完整体数据上复核。
2. **原稿没有运行过渲染器**。高斯传输函数、光照模式 7、多截图脚本等都是读代码得出的推断，实施计划把它们列为必须先做的验证实验（Spike）。本次整合同样没有新增渲染实验。
3. **“哪个物体是教堂”是推断**。官方圣诞卡写明雪景球里是大教堂模型，我把约 0.28 的块状物认作它。需要你在候选缩略图上确认一次，确认结果就是评测用的真值。
4. 文档没有写任何实现代码，07 只给出计划和接口契约。
