# 01 诊断报告：为什么 qwen3.6:35b 在这个任务上表现不佳

> 证据标签：【实测】来自日志、截图、仓库代码；【推断】由实测推理，未经实验；详见 `00-README.md`。

## 1. 摘要

1. 【实测】两次运行的最终画面里都**没有教堂**。run b 选中的是 5 个金属件，run a 选中的是 12 个金属件的侧视图。
2. 【实测】40 次 `render_scene` 调用（run a 22 次、run b 18 次；其中 39 次成功执行）里，`tfStart` 最小值是 0.5，**没有一次探测过 0.5 以下**。
3. 【实测】切片里量到的密度（renderer-uint8 除以 255）：礼盒壁 0.16–0.24，疑似教堂的块状物约 0.28，块状物下方的亮色小造型 0.49–0.53，玻璃球壳 0.6–0.78，12 个小金属件大于 0.9。教堂在这个排序里偏低，不是偏高。
4. 【实测】渲染器当前暴露的传输函数是单调高通 smoothstep，**结构上做不到**“显示 0.28、隐藏 0.6 以上的球壳”。渲染器本身其实支持高斯传输函数、自定义传输函数和带光照的模式，但 `src/renderer.py` 把它们写死关掉了。
5. 【推断】这是工具设计问题叠加信息缺失，不是模型“不够聪明”一个原因能解释的。换更强的模型而不改工具，上限依然很低。

## 3. 核心发现：搜索方向反了

### 3.1 密度实测

数据来自 run a 保存的 8 张体素切片（z=100、105、110、110 与 x=120、122、123、123），数值域为 renderer-uint8。

| 结构 | 归一化密度 | 备注 |
|---|---|---|
| 礼盒壁 / 包装 | 0.16–0.24 | 薄壁，部分体素效应 |
| 球颈基座上的块状物（顶部带垛口） | ≈0.28（0.25–0.30） | 我判断是教堂模型，见 `02-dataset-facts.md` |
| 块状物下方的亮色小造型 | 0.49–0.53 | 身份不明，可能是“隐藏的小生物”或底座部件 |
| 玻璃球壳 | 0.60–0.78 | 只有 1 到 2 个体素厚，最亮的大结构 |
| 12 个小件（推断是金属紧固件） | 大于 0.9 | 在 run a 末段 tfStart 0.9 时仍可见 |

### 3.2 两次运行都没有读到这张表

- 两个 agent 在第一次 `inspect_scene` 之后都立刻把 `tfStart` 抬到 0.5，理由是“教堂密度应该比盒子和球更高”。这个前提没有任何数据支持。
- 之后 40 次渲染调用里 `tfStart` 从未低于 0.5，所以 0.28 附近的教堂本体一次都没有进入过任何画面。
- 它们看到的“教堂”是球壳（沿 z 轴俯视时是同心环）和金属件（侧视时是 3×4 的点阵）。

### 3.3 模型其实碰到了矛盾，但没有工具去解决它

run a 的最终总结里，模型自己写到：压低盒子和球所需要的高阈值，同时也把教堂的大部分去掉了，所以教堂只剩零散碎片。这正是单调高通传输函数的困境。但它的结论是“教堂是碎片化的致密结构”，而不是“方向错了”，因为它没有任何办法检验“教堂到底多密”。

## 4. 根因

编号对应 `03-architecture-before-after.md` 中旧流程图的红色节点。

### R1　工具形状错：只有单调高通传输函数，且无光照【实测】

- `src/renderer.py` 生成的 GSC 脚本写死了 `settfparams false`（smoothstep：低于 start 全透明，高于 start+width 全亮）、`setmethod 0`（无光照）、正交相机。
- 原生渲染器的 `settfparams true` 是高斯窗（天然带通），`settfcode` 与 `settffile` 能载入任意 RGBA 传输函数，`setmethod 7` 起是带光照的渲染模式。这些能力都没有暴露。
- 后果一：不可能“只显示中间密度”。后果二：没有光照，画面是没有深度的白斑，模型描述成“点”和“环”，几何判断更差。
- 置信度：高。

### R2　信息不对称：直方图已经算好，却没有给模型【实测】

- `src/volume.py` 的 `prepare()` 已经算出完整精确直方图并写进 `volume.json`，但 `ExternalTools.snapshot()` 只回传 dimensions、geometry、orientation 等字段，不含统计。
- 模型也没有“读某个位置体素值”的工具，所以看到切片里一个灰色块，无法知道它是 0.28 还是 0.8。
- 后果：模型只能编造数值。run b 的最终总结断言“球的密度约 0.4–0.6”，而实测球壳是 0.6–0.78；run a 看到切片后认为“教堂比光线投射画面显示的要密得多”，于是把 tfStart 继续抬到 0.85 和 0.9，离真值更远。
- 置信度：高。

### R3　没有可验证的目标【实测】

- `finish_task` 的返回里 `taskSuccess` 永远是 `unverified`，唯一的客观反馈是“非黑像素数”，它不区分教堂和金属件。
- run b 在没有教堂的画面上宣布成功；run a 承认画面碎片化，但因为预算耗尽只能收工。
- 后果：没有任何信号告诉模型“你选错物体了”，也没有信号可以用来做自动搜索或离线评测。
- 置信度：高。

### R4　上下文压缩摧毁视觉记忆，错误信念被固化【实测】

- run a 压缩 6 次，run b 压缩 2 次。压缩后图片丢失，只剩文字摘要；摘要里是模型自己写的推断，被当作事实继续传递。
- 例子一（run b）：模型根据“tfStart 0.7 时中间的球消失了”推出“教堂密度大于 0.7”，这条写进摘要后成了后续决策的前提。
- 例子二（run a）：摘要把“教堂位置在 x=120–123”当作事实，但那只是它看过的切片索引，不是教堂的空间坐标。
- 两次运行的配置都是 `contextSize` 16384【实测，来自 `run.json`】；Codex 对 `qwen3.6:35b` 使用了回退元数据，自动压缩阈值可能并不匹配实际窗口。
- **`contextSize` 只配置了 Codex 一侧**【实测，来自代码】：`scripts/run_local_agent.py` 把它写成 Codex 的 `model_context_window`，而转发给 Ollama 的请求体里，代理只改写了 `temperature` 和 `think`，没有设置 `num_ctx`。所以 Ollama 实际使用的上下文长度取决于服务端或模型自身的默认值。如果它小于 Codex 以为的窗口，较早的消息（包括系统提示和工具定义）可能被 Ollama 静默截断【待验证，用 `ollama ps` 查看运行中模型的实际上下文长度】。这与“压缩频繁、早期事实丢失”的现象相容，但本次数据无法证明它确实发生。
- 置信度：中高。压缩次数是实测，“压缩导致错误固化”是因果推断，但两个例子的文本证据比较直接。

### R5　空间接地断链：切片像素无法换算成 crop 坐标【实测】

- run a 在 x=120、122、123 的切片里多次描述“球内有一个带塔尖的建筑结构”，这个观察本身是对的。但切片的行是 z、列是 y 这一约定没有告诉模型，也没有任何工具把“切片里的某块区域”变成 crop 边界，所以这条线索没有转化成行动。
- run b 凭“大概在每个维度的中间三分之一”猜了 crop `[80,166,80,166,80,141]`，没有数据依据。按我的测量，块状物在 z 方向约 119–149，这个 crop 的 z 上限 141 会把它截掉一部分【推断】。
- 黏性参数混淆：`render_scene` 的“省略的参数保持不变”规则让 crop 一直残留。run b 的 crop 从 rev 5 起生效，rev 10、11 两帧完全是黑的（亮像素 0），模型花了好几次调用才意识到是自己之前设的 crop 还在生效，rev 12 才恢复全体积。同时改 crop 和 tfStart，也让它无法归因，先错怪 crop，后来又错怪 tfStart。
- 置信度：高。

### R6　采样与决策结构：单变量爬山加重复动作【实测】

- 两次运行的配置都是 temperature 0、`think=true`（Codex 侧 `reasoning_effort=medium`）【实测，来自 `run.json`】。run b 里有 3 组完全相同的帧（rev 3=16、7=8、10=11），run a 有 1 组（rev 11=13），说明 temperature 0 下模型会原样重复同一个动作。
- TUI 里每次的“思考”显示为 0 秒，但 `harness.jsonl` 里有完整的 reasoning 文本。这是显示或时间戳统计问题（TUI 没有把 reasoning 事件的耗时算进“Thought for”），**不是 think 关闭**【实测】。
- 整体策略仍是沿 `tfStart` 一个维度的爬山，没有“提出假设、设计实验、检验假设”的结构，也没有探测过相反方向；reasoning 主要用于给已经选定的阈值找理由。
- 置信度：中高。重复帧和 reasoning 的存在是实测，“思考没有转化为探索”是对 reasoning 文本的判断。

### R7　视觉感知错误与自信的幻觉【实测 + 推断】

- 【实测】两个 agent 把 12 个纺锤形金属件的 3×4 点阵描述成“排成行的小教堂”和“带塔楼的建筑”；run b 把它们叫作“柱子和拱门”。
- 【实测】run a 说教堂是切片里“最亮的白色物体”，但按实测，最亮的大结构是玻璃球壳，块状物只有约 0.28 的灰度。
- 【推断】`qwen3.6:35b` 是稀疏专家结构，每个 token 只激活约 3B 参数，这类模型的视觉定位和空间推理比同体量稠密模型更弱，是上述幻觉的一个合理贡献因素，但本次数据无法单独量化它的作用。
- 置信度：感知错误本身高，归因于模型结构低。

## 5. 被排除或次要的因素

| 因素 | 判断 | 依据 |
|---|---|---|
| 渲染延迟 | 次要 | 每帧约 3 秒，整个 run 的时间主要在模型推理 |
| MCP 传输或图像回传故障 | 排除 | 图像带 sha256 校验，回传内容与落盘一致 |
| 渲染器正确性 | 排除 | 每次渲染都有原生状态回读校验（tf、crop、旋转、分辨率）通过 |
| 观察预算太小 | 次要 | run b 没用满预算也失败；run a 用满 30 次但方向本身是错的 |
| 模型拒绝使用工具 | 排除 | 两个 run 都按协议调用并正常 `finish_task` |
| 任务描述含糊 | 部分成立 | “chapel”在数据里是一个没有文字标签的数值块，需要“看图选择”这一步；但这是工具设计要解决的，不是 prompt 措辞能解决的 |

## 6. 反事实检验【推断，待用 Spike 验证】

如果当时工具支持高斯窗并附带直方图：

1. 第一帧后模型会拿到直方图，看到除背景外在约 0.28、约 0.5、0.6 以上都有结构，搜索会从 0.28 开始，而不是 0.5。
2. 使用 `settfparams true 0.28 0.02`，礼盒壁（≤0.24）和球壳（≥0.6）都落在窗外，块状物居中。球颈基座附近的 crop（约 y 106–147、z 117–150，x 以球心约 124 为中心）能进一步压低残留。
3. 这条链上的每一步，都需要实施计划里的 Spike S2、S3（见 `07-worker-implementation-plan.md`）在真实渲染器上跑通才算数。
