# 06 评测协议

> 目标：把“成功”从模型自述变成可计算的量，并让不同配置之间的比较有统计意义。证据标签见 `00-README.md`。本协议里的阈值是**建议初值**，必须先用第 4 节的正负对照校准，再冻结。

## 1. 原则

1. **成功由程序判定**，不由模型自述、不由 VLM 打分。
2. **真值对 agent 不可见**：真值文件不在 `runtime/` 下，不在任何 MCP 工具能读到的路径里，也不出现在任何提示词里。
3. **真值用节点签名**（平均密度、包围盒、体素数），不用节点编号，因为编号可能随参数变化。
4. **新旧流程用同一个评分器**。旧的 run a、run b 最终帧必须能被评分，并且预期被判失败。
5. **每次只改一类因素**（见 `05` 第 5 节的实验阶梯），每档重复运行，报告置信区间。

## 2. 成功的定义

### 2.1 输入

- 一次运行的最终帧：`final/image.png`、`final/scene.json`、以及该帧所用体数据的绑定信息（新流程会写 `volume-binding.json`，旧流程的帧用的是原体数据）。
- 真值文件：`eval/golden/christmas-present.json`（格式见 `02` 第 6.2 节）。
- 会话里的原始体数据（`runtime/<session>/volume/`）。

### 2.2 步骤

1. 用与 `analyze_structure` 相同的确定性算法重新分析体数据，得到节点表。
2. 把真值里的每个 `targets` 签名匹配到节点：平均密度差不超过容差，包围盒交并比不低于 `bboxIouMin`，体素数不低于 `minVoxels`。匹配不到则评分器报错，要求重新标注，而不是静默通过。
3. 取该帧所用体数据的窗口（原体数据的窗口是全体积），生成“只含目标节点”的参考体数据，用**同一个 scene**（相机、crop、旋转）渲染一张参考图。参考图固定使用无光照模式和低阈值的 smoothstep，使“非黑像素”只反映几何覆盖，不受光照明暗影响。
4. 计算两个掩膜：
   - `F`：候选帧的非黑像素，即任一通道大于 `pixelThreshold`（建议初值 8，满量程 255）。
   - `R`：参考图的非黑像素。
5. 指标：

| 指标 | 定义 |
|---|---|
| `coverage` | `|F ∩ R| / |R|`，目标有多少被画出来了 |
| `leak` | `|F \ dilate(R, r)| / |F|`，画面里有多少像素不能被目标解释，`r` 建议初值 2 像素 |
| `framePixels` | `|F|`，用来排除近乎全黑的退化帧 |

6. **成功** = `coverage ≥ coverageMin`（建议 0.8）且 `leak ≤ leakMax`（建议 0.05）且 `framePixels ≥ minFramePixels`（建议 500）。

### 2.3 这个指标证明什么、不证明什么

- 证明：画面里画出了真值指定的物体，并且几乎没有别的物体。
- 不证明：画面“好看”或“可辨认”。例如从一个看不清结构的角度渲染也可能通过。所以要加第 5.4 节的盲评。
- 不证明：真值本身对。真值是人工标注的，错标会让所有结论失效，见第 7 节。

## 3. 评分流程与产物

```
eval/
  golden/christmas-present.json     人工标注，对 agent 不可见
  score_run.py                      对一个运行目录评分，输出 score.json
  summarize.py                      汇总一个批次或多个配置，输出表格和 CSV
  calibrate.py                      第 4 节的正负对照校准
  results/<日期>-<配置名>/          每次实验的原始评分与汇总
```

`score.json` 字段：

```json
{
  "runDirectory": "...",
  "sessionId": "...",
  "frameRevision": 18,
  "coverage": 0.0,
  "leak": 1.0,
  "framePixels": 2365,
  "success": false,
  "failureCode": "F1",
  "thresholds": {"coverageMin": 0.8, "leakMax": 0.05, "minFramePixels": 500, "pixelThreshold": 8, "dilate": 2},
  "volumeHash": "...",
  "analysisHash": "...",
  "matchedTargets": [{"annotatorNote": "...", "nodeSignature": {}}]
}
```

## 4. 校准：正负对照（必做）

在冻结阈值前，用已知答案的帧检验评分器本身：

| 类型 | 构造方式 | 期望 |
|---|---|---|
| 正对照 | 用真值目标的派生体数据，以 5 个以上不同相机（含正面、侧面、斜 45 度）渲染 | 全部判成功 |
| 正对照（带光照） | 同上但开启光照模式 | 全部判成功，验证光照不会误伤 |
| 正对照（高斯窗） | 在原体数据上用高斯窗加 crop 渲染目标 | 如果泄漏很小应判成功，否则据此调整 `r` 和 `leakMax` |
| 负对照 | 只渲染球壳、只渲染礼盒、只渲染金属小件 | 全部判失败 |
| 负对照 | 原体数据的默认第一帧 | 判失败 |
| 负对照 | 旧的 run a、run b 最终帧 | 判失败；如果被判成功，评分器有问题 |
| 退化对照 | 全黑帧 | 判失败，`failureCode` 指向“空帧” |

校准结果写进 `eval/results/calibration.md`，记录每个阈值取值的依据。校准之后冻结阈值，之后改阈值必须作为新版本的协议。

## 5. 运行协议

### 5.1 配置与可复现性

- 每个实验档位用一个冻结的配置文件（见 `07` 的 `experiments/` 预设）。
- 每次运行都记录：配置的 sha256（`run.json` 里已有 `configSha256`）、模型的摘要信息（启动器已写入 `model.json`）、仓库的 git 提交、`volumeHash`、`rendererSha256`、Ollama 实际生效的上下文长度。
- 不同档位**交错运行**（E0、E1、E2、E3、E0、E1……），而不是各跑 10 次再换下一档，以减少机器状态漂移的影响。
- 同一台机器、不同时跑别的 GPU 任务。
- 每档至少 10 次运行；如果要检测较小的差异，增加到 20 次。
- 因为通过本地推理服务无法固定随机种子，每次运行视为独立样本。

### 5.2 记录的指标

| 类别 | 指标 |
|---|---|
| 主指标 | 程序化成功率 |
| 质量 | `coverage`、`leak` 的分布 |
| 效率 | 观察预算用量、工具调用总数、墙钟时间、输入和输出 token、上下文压缩次数 |
| 行为（旧工具） | 首次 `tfStart` 探测值、`tfStart` 最小值、重复帧数 |
| 行为（新工具） | 选到的节点是否在真值内、`verify_frame` 首次通过率、回退次数 |

### 5.3 失败分类

每个失败运行归入一类，便于看哪类根因被解决了：

| 代码 | 含义 | 对应根因 |
|---|---|---|
| F1 | 画面里没有目标（选错物体或阈值错误） | R1、R2 |
| F2 | 目标出现，但泄漏过大 | R1、R5 |
| F3 | 目标被截断或被 crop 切掉 | R5 |
| F4 | 观察预算耗尽仍未得到合格帧 | R6 |
| F5 | 提前结束，没有调用 `finish_task` | R6 |
| F6 | 工具或渲染报错导致中断 | 实现问题，不计入方法比较，需单独复盘 |
| F7 | 空帧或近乎空帧 | R5 |

### 5.4 盲评（可选，建议做）

程序化指标不衡量“能不能认出这是教堂”。在最终报告前，把各档位的最终帧随机打乱并隐去档位信息，请标注者按 1 到 5 分评“能否辨认出目标物体”，作为补充指标。建议至少评 20 张。

## 6. 统计方法

1. 成功率用 **Wilson 区间**报告 95% 置信区间。比例 `p`、样本数 `n`、`z = 1.96` 时，区间中心为 `(p + z²/(2n)) / (1 + z²/n)`，半宽为 `z·√(p(1-p)/n + z²/(4n²)) / (1 + z²/n)`。
2. 两个档位的成功次数比较用 **Fisher 精确检验**（双侧）。
3. 只做预先登记的相邻比较：E1 对 E0，E2 对 E1，E3 对 E2，E4 对 E3，不做所有两两比较，避免多重比较膨胀假阳性。
4. 提醒：每档 10 次时，7 次成功的 95% 区间大约是 39% 到 90%，2 次对 8 次的差异才勉强达到常规显著水平。差异不大时，不要下结论，加样本。
5. 连续指标（`coverage`、`leak`、token、时间）报告中位数和四分位区间，不报告均值。

## 7. 防泄漏与防作弊

1. 真值文件放在 `eval/golden/`，该目录不在 `runtime/` 里，渲染服务的 `/artifact/` 路由只服务 `runtime/` 下的文件，因此 agent 看不到它。
2. 提示词、工具描述、工具返回里不出现真值内容；节点标签只有数值。验收时做一次文本检查：在 `src/`、`scripts/`、`experiments/` 里搜索 `golden`、`chapel`、`cathedral`，不应出现在任何会发给模型的字符串里。
3. 标注者看过联系表，难免带着对数据的先验；真值错标是最大的系统性风险。缓解：同一人隔天复核一次，或第二个人独立标注，不一致的节点重新讨论。
4. 评分器的阈值在看到 E1 到 E4 的结果**之前**冻结。

## 9. 已知局限

1. 只有一个数据集和一个任务文本，结论不能外推。阶段 1 的合成体可以做泛化检验，但合成体与真实 CT 的分布不同。
2. 评分器依赖本项目自己的结构分析算法来匹配真值，如果这个算法在别的数据上失效，评分也会失效。
3. 非黑像素掩膜无法区分“目标本身”和“目标前面被遮挡的东西”，所以仍需要盲评作为补充。
